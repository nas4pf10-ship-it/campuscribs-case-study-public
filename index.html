01 / Overview

One platform, three user journeys.

The product is organized around the different responsibilities involved in finding and managing student accommodation. The engineering challenge is to keep those workflows distinct while coordinating identity, listing data and reservation state.

Students

Explore accommodation, inspect hostel and room details, and follow reservation requests.

Hostel owners

Manage hostel and room information, review incoming reservations, and confirm or decline requests.

Administrators

Use a protected administration area for hostel review, verification and moderation workflows.

03 / Core workflow

Reservation lifecycle.

Key booking transitions are routed through named backend operations rather than being represented only as local interface state.

Step 01Discover a hostel
Step 02Select a room
Step 03Request reservation
Step 04Host reviews request

Backend operations

Inspected booking hooks call database operations including reserve_room, student_contacted_host, host_confirm_student_booking and host_decline_booking.

Consistency considerations

Reservation systems need authoritative state transitions, valid room references, concurrency handling and consistent student/host views. Migration logic inspected includes row-locking behavior; full deployed guarantees still require testing.

04 / Engineering decisions

Make important domain actions explicit.

Role-specific workspaces

Dedicated student, host and administrator route areas make each user journey clearer. Route checks are a navigation and UX control, not a replacement for database authorization.

Backend-owned booking transitions

Named RPC operations provide a central place for reservation rules. Their correctness depends on database logic, permissions and policies being tested alongside the frontend.

Server-side payment integration

Edge Functions keep provider secret handling out of browser code. Payment and booking state still need careful reconciliation, retry handling and validation.

Progressive web app foundation

The project includes Vite PWA and Workbox tooling as part of its web application stack.

05 / Payment integration

Implemented integration logic; not a live-payment claim.

The codebase contains Paystack initialization, verification and webhook-handling logic. The webhook path includes HMAC SHA-512 signature validation.

Known issue found during source review

Inspected Edge Function code uses a GH₵50 booking-fee value, while inspected database migration logic references GH₵100. The discrepancy must be reconciled across the client, Edge Functions and database workflows before live payment use. The verification path also needs fail-closed handling when database confirmation fails.

Accordingly, this portfolio page does not claim that live student-facing payment processing is enabled, end-to-end correct or production-validated.

06 / Verification boundaries

What this case study does—and does not—claim.

Visible in source

  • Role-aware student, host and admin route areas.
  • Supabase authentication and PostgreSQL-backed workflows.
  • Named reservation RPC call sites.
  • Paystack integration code in Edge Functions.
  • PWA tooling in the frontend stack.

Not independently verified

  • Complete live RLS policy and database grant coverage.
  • End-to-end payment correctness or live transactions.
  • Full automated test-suite results.
  • Production deployment, monitoring, backup and recovery.
  • Commercial adoption, active users or transaction volume.

Interactive maps are not presented as implemented; the inspected map experience indicates that the feature is coming soon. No production-readiness or security-audit certification is implied.

07 / Next engineering priorities

Close the gaps before production claims.

  1. Reconcile booking-fee configuration across all payment paths.
  2. Validate payment amount, currency, reference, ownership and booking state; fail closed if database confirmation fails.
  3. Test webhook idempotency and duplicate-event handling.
  4. Audit RLS policies, function grants and direct API authorization.
  5. Add automated tests for role boundaries, reservation concurrency and payment failure paths.
  6. Run controlled end-to-end tests in Supabase and Paystack sandbox environments.
  7. Verify deployment operations, observability, backups and recovery.
